> 比真实浏览器慢，会**高估**渲染占比；真实浏览器里渲染 share 更低，故下述天花板是乐观上界。

## 3. 数据流/结构分析（候选前提不成立）

逐行核对主循环（`documentRenderer.ts:435–552`）后确认：

1. **已是单趟、已批量**：段落循环只走一遍；`addToPage` 是数组 push + 高度累加，
   `finalizePage` 每页只做一次 `join('\n')` 后 `result.push` —— 这正是「批量化」本身，
   不存在被遗漏的第二趟组装或 O(n²)。
2. **无可合并的边界**：每段/每单元格产出的 HTML 相互独立（表格行还依赖列合并/边框状态），
   不存在「攒一批一起算」的共同中间量；所谓「批量化」没有可操作的语义目标。
3. **表格相关热点是正确性敏感区**：`renderRow`/`splitTableCells`/`buildCellStyle`/
   `collectTableBlock` 承载跨页切分、垂直合并降级、单元格边框等已反复修复的逻辑，
   属 Phase 3 正确性原则，不是可随手合并的重复计算。

## 4. 裁决

- **收益天花板 < 1.2% 且不可达**：唯一与「分页批量化」直接相关的 `finalizePage` 仅占
  端到端 ~1.2%，即便 100% 消除也只是 1.2%，而它已完成批量（单 join），实际可省趋近于 0。
- **无结构性浪费**：R179/R180 已证解析器无 O(n²)/重复整趟；本轮证伪渲染侧「批量化」
  前提 —— 单趟循环 + 每页单次 join 已是最简形态。
- **噪声地板 ~55% 与门槛**：R177–R181 五连否决，本机配对胜率噪声地板 ~54.7%，
  采纳需 >57% 胜率 + 27 份逐字节等价；本轮无任何可通过该门槛的候选。
- 按章程「证据不足即否决、不留变慢/未证代码」⇒ **撤回，未落地任何代码**。

**通用教训 20**：当剖析显示「渲染占端到端 55%」时，必须继续下钻到函数级自耗再判方向。
若热点全在逐元素的必要字符串生成（且装配本身已用「数组 push + 单次 join」批量化），
则「批量化」是无的放矢；此时渲染占比高只说明它**重要**，不说明它**有可省的重复趟**。
