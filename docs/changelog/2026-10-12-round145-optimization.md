# Round 145：`buildMagicScanIndex` 改为「Uint16 一次读一对」（并否决其展开/闭包变体）

## 结论与候选

采纳「`buildMagicScanIndex` 的单趟扫描不再逐字节取两字节再拼索引，改用 `Uint16Array` 视图**一次读出一对**」
候选。**同时否决了同一想法的高展开变体**（闭包 + 2/4 对展开），理由是它在端到端上**退化**——这一否决
本身就是本轮最有价值的发现。

- **前提（`--cpu-prof` 剖析，80 轮 × 27 份语料）**：`buildMagicScanIndex` 是整轮**第 4 大自耗项，5.39%**
  （前三为 `createParagraphsWithRealFormats` 12.99%、GC 10.54%、`applyStructuralFormats` 10.81%）。
  行级归因显示最热的一行正是 `PAIR_HAS_LEAD[(data[i] << 8) | data[i + 1]]`，**单行 2.97%**——
  每个 2 字节窗口要付两次字节读取 + 一次移位 + 一次或。
- **隔离基准（9 锚点、27 份真实 `WordDocument` 流共 5,767,130 B、配对 60 轮）**：

  | 变体 | 中位 (ms) | 相对现状 |
  |---|---|---:|---:|
  | A 现状（逐字节取两字节 + 移位拼索引） | 4.080 | — |
  | G 两张 256 字节小表代替 64 KB 字节对表 | 4.411 | **慢 9.2%**（再次证实 64 KB 表不是瓶颈） |
  | **F `Uint16Array` 一次读一对（无展开、无闭包）** | **3.625** | **快 10.3%** |
  | H = F + 2 对展开（闭包 `pushAt`） | 2.907 | 快 28.8% |
  | J = F + 4 对展开（闭包 `pushAt`） | **2.771** | **快 32.1%** |

  H / J 在隔离配对里 **60/60 全胜**；三者桶内容与 `imageCandidates` 与 A 逐元素一致。
- **端到端（相邻交错配对，逐对反转顺序）——决定性的反例**：
  - **J（4 对展开 + 闭包）**：n=400 → CAND 中位 86.275 / BASE 86.111 = **−0.191%**，
    配对差均值 **−0.678 ms（−0.788%）**，**胜 199/400（49.8%）**，块 10/20 为正。⇒ **否决**。
  - **F（无展开、无闭包）**：三次独立测量一致为正 ——
    n=400 → 中位 **+1.381%** / 均值 **+1.598%** / 胜 **264/400（66%）** / 块 **18/20 为正**；
    n=400（块 40）→ 中位 **+1.161%** / 均值 **+1.600%** / 胜 **265/400**；
    最终源码 n=300 → 中位 **+1.421%** / 均值 **+1.758%** / 胜 **198/300**。
    ⇒ **采纳**。
- **等价性**：27 份完整 `parseWithFormat` 结果 **16,247,039 字符逐字节一致**。
- `bench-diff 145` 与 `144` 除 `cycle`/`timestamp` **逐字段相同**（`median` 仍为 0.9502433994244857）。
- 包体（同工具链 HEAD 基线对比）：`doc-preview.js` raw **+617 B** / gzip-9 **+162 B**；
  `umd.cjs` raw **+415 B** / gzip-9 **+151 B**（增长主要来自记录上述 JIT 陷阱的文档注释）。
- 拟从现场 0.7.65 升至 **0.7.66**。

## 本轮最重要的发现：隔离微基准会「过度升层」，赢家必须在真实调用模式下复核

J 变体在隔离微基准里 60/60 全胜（4.080 → 2.771 ms，快 32%），端到端却**退化 0.788%**。
原因是**调用频次改变了 JIT 层与内联决策**：

- 隔离基准在一个紧循环里把同一份 5.77 MB 数据连扫 40～60 遍，函数被 V8 升到最高优化层，
  **闭包 `pushAt` 被内联**，于是展开省下的循环开销净赚；
- 真实一轮里 `buildMagicScanIndex` 只被调用一两次，函数停在较低层，**闭包调用没有被内联**，
  展开后每组命中要付 8 次真实调用，开销超过省下的循环开销。

去掉闭包与展开（只保留「一次读一对」）后，同一份想法端到端变为 **+1.60%（均值口径）**。
⇒ **教训：微基准里「更快」的写法，如果引入了新的函数调用边界或依赖内联，必须在真实调用频次下
用端到端配对复核后才能落地；隔离基准只用来筛方向，不能定值。** 这条与 Round 103
（隔离 1.47× / 端到端 −7%）和 Round 142（亚 1% 阈值）同属一类，但机制不同：前两者是
**工作量占比**问题，本轮是 **JIT 层/内联**问题。

## 实现

改动只落在 `src/utils/docparser/magicScanIndex.ts` 的 `buildMagicScanIndex`（+73/−5，含文档注释）。

- 新增模块级 `const MAGIC_LEAD_COUNT = MAGIC_SCAN_LEADS.length`（供槽位判定与建桶复用）。
- `len === 0` **提前返回**空结果：一是空输入本就产出空结果；二是**已分离（detached）的 ArrayBuffer**
  上视图 `length` 归零，若仍去构造 `Uint16Array` 会抛 `TypeError`，而旧实现只是安静返回空桶。
- **快路径**（`data.byteOffset` 为偶数）：`new Uint16Array(data.buffer, data.byteOffset, len >> 1)`，
  循环体只剩「一次数组读取 + 一次查表 + 一次比较」；命中时**逐字节**查 `LEAD_SLOT`（两个字节都查），
  按字节递增顺序 push；奇数尾字节单独收尾。
- **慢路径**（`byteOffset` 为奇数，无法建 `Uint16Array` 视图）：退回逐字节对推进 + 移位拼索引，
  语义与快路径一致。真实 27 份 `WordDocument` 流实测 `byteOffset` 全为偶数（27/27），
  但 `readStream` 之外的调用方可能给出奇数偏移的子视图，故回退分支必须保留。
- **端序无关**：`PAIR_HAS_LEAD` 的构造对调换高低字节**对称**（同时写 `(lead << 8) | other`
  与 `(other << 8) | lead`），所以小端机器上 `u16[j] === (data[2j+1] << 8) | data[2j]`（字节序相反）
  与大端机器上的 `(data[2j] << 8) | data[2j+1]` **都能命中同一张表**，无需运行时端序探测。
  「表对称」因此是这条快路径的**正确性前提**，护栏用「只填一半的字节对表」作负控钉住它。
- 未改动：`SCAN_LEADS`/`MAGIC_SCAN_LEADS`/`LEAD_SLOT`/`PAIR_HAS_LEAD` 的构造、
  `MagicScanIndex` 接口、`nextMagicOffset`（含 `from` 归一化与图片首字节退回原生）。

## 护栏

`tests/magicScanIndex.test.ts` 从 31 项扩至 **46 项**（+15），新增一个 Round 145 段落：

**① 快路径 == 慢路径**：27 份真实流 + 对抗流 + 300 条随机流上，把同一段逻辑字节分别放在
偏移 0（走 `Uint16Array` 快路径）与偏移 1（走逐字节慢路径），断言桶与 `imageCandidates` **逐项相同**；
并断言 `shifted.byteOffset % 2 === 1`（否则用例空转）、候选总数 `> 50000`（否则可能只是「两边都空」）。
另单独断言 27 份真实流的 `byteOffset` 全为偶数（快路径前提）。

**② 边界与尾部出口**：长度 **0..40 全枚举**（铺满单一首字节 / 交替 `0xd0`·`0x41` 两种相位），
每种都与「逐个原生 `indexOf` 的完整枚举」比对；锚点落在 0/1/3/4/7/8/9/15/16/23/24/31 任意位置
（含对边界）都被收录；末字节是魔数首字节或图片首字节时都被收尾。

**③ 回退保障**：空输入返回空桶空候选；**已分离的 ArrayBuffer** 上用 `structuredClone(ab, { transfer })`
制造 `length === 0` 的视图，断言不抛错且返回空结果。

**④ 鉴别力**：与生产快路径**同构**的骨架 `buildFastSkeleton`（正控 `PUSH_BOTH` + 收尾必须与 oracle 相同）
注入 4 个故意改错必须被检出：①一对里只查第一个字节 ②一对里只查第二个字节 ③漏掉奇数尾字节
④**字节对表只填一半**。另有一条**端序无关性**的元断言：夹具
`[0xd0, 0x41, 0x41, 0xd0]` 在两种字节序下各有一对会被非对称表漏掉，故「必须被检出」不依赖机器端序；
同一输入换成对称表则完全一致，证明差异只来自表的一半缺失。慢但等价的对照
（两趟计数建表 `bucketizeTwoPass` / `imageCandidateTwoPass`）必须与新的单趟扫描逐项相同。

**离树负控注入**（改生产源码 → 跑同一护栏 → 逐项恢复）：
- NC-A 删掉奇数尾字节收尾：**11 项失败**；
- NC-C 字节对表只填一半：**25 项失败**；
- 恢复后 **46/46 全绿**。
（原 J 变体时期的 NC-B「漏掉展开后半」在改为无展开实现后不再适用，已随实现一起移除。）
