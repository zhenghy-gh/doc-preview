# Round 100 — 两趟空转的流扫描改用条件式 `indexOf` 跳跃

日期：2026-10-08
版本：0.7.43 → 0.7.44
基线：`8355d5c`（round 99）

## 起因：把 round 99 的方法用在更大的目标上

Round 99 给 `extractWordArtFromDrawingData` 加了条件式跳跃，它在 5.5 MB
真实语料上从 ~10.5 ms 降到 1.72 ms。但那只是四个「各自全扫同一个
WordDocument 流」的函数之一。本轮先量了四个函数各自的开销：

| 函数 | 中位数 | ms/MB | 真实语料产出 |
|---|---|---|---|
| `extractShapesFromWordDocumentStream` | 10.60 ms | 1.93 | 0 个形状 |
| `extractEquationsFromWordDocumentStream` | 11.05 ms | 2.01 | 0 个公式 |
| `extractChartsFromWordDocumentStream` | 10.53 ms | 1.91 | 0 个图表 |
| `extractWordArtFromDrawingData`（round 99 已优化） | 1.72 ms | 0.31 | 27 个 WordArt |

四趟合计 33.89 ms，其中 **32.2 ms 花在三个产出恒为 0 的扫描上**。Round 99
让 wordArt 比其余三个快 6 倍，本轮把同一个方法用在剩下三个中的两个。

## 三个扫描的锚点密度（实测，不是假设）

跳跃划不划算完全由锚点字节的密度决定，所以先量：

| 字节 | 计数 | 密度 | 平均间隔 |
|---|---|---|---|
| `0xEF`（公式魔数首字节） | 4 878 | 0.0846 % | 1 182 B |
| `0xF0`（形状前置筛的 `o+3`） | 6 752 | 0.1171 % | 854 B |
| `0xD0`（图表 OLE lead） | 6 610 | 0.1146 % | 872 B |
| `0x50`（图表 ZIP lead） | 30 439 | 0.5278 % | 190 B |
| `0x00` | 1 811 437 | **31.41 %** | 3.2 B |

`0x00` 的 31.4 % 又一次印证了 round 98 的更正：以 `0x00` 为锚点的方案必然退化。
形状的前置筛虽然同时要求 `o+2 === 0x00` 与 `o+3 === 0xF0`，锚点只能选 `0xF0`。

三个扫描的完整匹配次数（5.77 MB 语料）：形状前置筛 411 次、图表 lead **0** 次、
公式魔数 **0** 次。公式魔数是 `EF BF BD EF BF BD`，即 UTF-8 的 U+FFFD（替换字符）
重复两次——看着像从一段乱码里提出来的，在真实语料里一次都没出现。**本轮不碰它**
（改掉它是行为变更），只让扫描它变便宜。

## 图表：量了、算过、放弃

图表扫描的 lead 是 `0xD0`（OLE 的 `D0 CF 11 E0`）或 `0x50`（ZIP 的 `50 4B 03 04`），
所以要跳两个字节。第一版实现取两者的较小值：

```ts
const p = Math.min(d.indexOf(0xd0, o + 1), d.indexOf(0x50, o + 1))
```

**实测 6.72 ms → 940 ms（0.01x）**，退化 140 倍。计数后定位了原因：

```
landings   : 36996        （落地次数，符合 0xD0/0x50 的总出现数）
oleCalls   : 36973
zipCalls   : 36969
scanned    : 3690 MB      ← 不是 39 MB
```

每次落地只前进约 156 字节，却要把「到下一个 `0xD0`」的距离**重新扫一遍**。
因为 `0xD0`（0.11 %）比 `0x50`（0.53 %）稀 4.6 倍，朝较密的 `0x50` 前进的每一步
都在重扫那段到 `0xD0` 的长距离；而 `oleGone` 永远不会触发，因为那个 `0xD0`
每次都找得到。**取两个目标的最小值是二次方行为。**

「缓存两个目标位置、只在被越过时刷新」能把它拉回线性（**6.93 → 3.60 ms，1.92x**），
但：

* 需要 4 个状态变量（两个位置 + 两个「已耗尽」标记）；
* 「已耗尽」用 `-1` 表示会再次退化——`-1 <= o` 恒真，于是每次落地都重扫一遍
  到数组末尾，1 MB 全 `0xD0` 的输入直接把进程跑挂（基准里 exit 137）。

1.92x 换这么多复杂度与一个更差的最坏情况不划算。**本轮不动图表函数**，
把上面的测量留在这里，供日后决定是否值得。

## 改动

### `src/utils/equationParser.ts` — `extractEquationsFromWordDocumentStream`

两处，彼此独立：

1. **压平魔数比较。** 原先是内层 `for` 循环遍历一个 `Uint8Array` 魔数并维护
   `match` 标志；改成 5 个直接常量比较。这一项单独就有 **1.76x**。
2. **条件式跳跃。** 首字节不等于 `0xEF` 时 `offset = data.indexOf(0xEF, offset + 1)`。
   魔数比较的第一项就是首字节，所以首字节不匹配时比较必然失败——跳到下一个
   `0xEF` 不会漏掉任何候选，被接受的偏移集合与逐字节版本完全一致。

两项合计 **6.79x**。新增模块级常量 `EQN_MAGIC` / `EQN_MAGIC_LEAD` / `EQN_MAGIC_LEN`，
从魔数派生而不是另写字面量，两者不会日后漂移。

### `src/utils/shapeParser.ts` — `extractShapes`

前置筛失败时跳到下一个 `0xF0` 并回退 3 字节：

```ts
if (data[offset + 2] !== FDG_TYPE_LO || data[offset + 3] !== FDG_TYPE_HI) {
  if (data[offset + 4] === FDG_TYPE_HI) { offset++; continue }
  const p = data.indexOf(FDG_TYPE_HI, offset + 4)
  if (p < 0) break
  offset = p - 3
  continue
}
```

落在 `[offset+1, p-3)` 之间的偏移其 `o+3` 处都不是 `0xF0`，前置筛必然失败，
跳过它们不会漏掉候选。控制流从 `for` + `continue` 改成 `while` + 嵌套判断，
使非跳跃路径只有一个 `offset++`。

**「锚点紧邻就不跳」这层守卫是必需的。** `indexOf` 即使立刻命中也要付一次原生
调用；锚点铺满时每次只前进 1 字节，就变成「每字节一次调用」。实测 1 MB 全 `0xF0`：

| | 1 MB 全 `0xF0` | 真实语料 |
|---|---|---|
| 无守卫 | 1.46 → 9.10 ms（**0.16x**，退化 6 倍） | 6.48x |
| 有守卫 | 1.28 ms（1.14x） | 6.40x |

守卫的代价在真实语料上是 1.2 % 的相对损失，换来最坏情况不再退化。

## 等价性证据

四重：

1. **真实语料差分。** 27 份 `.doc` 整文件上，新旧实现在两个函数上逐字段一致；
   两版产出都是 0（已知事实，写进断言而不是当作通过）。
2. **合成语料差分。** 公式 14 例、形状 13 例，逐条断言「该不该产出」。
   公式的合成块构造出合法魔数 + UTF-16LE 文本 + `0x0000` 终结符，能真的产出
   公式——这是这份差分测试有意义的前提（见下面的坑）。
3. **确定性模糊。** mulberry32 各 400 组随机缓冲区，一半从「可疑字节表」取字节、
   四分之一植入真魔数或真 FDG 链，逐字段比对。
4. **阴性对照。** 造 6 个改错的实现，要求差分测试抓出来；另造 2 个「更慢但
   行为等价」的实现，要求差分测试**不**报差异（否则说明它过度敏感，会把等价
   优化误判成行为变更）。

| 对照 | 内容 | 期望 | 实测 |
|---|---|---|---|
| A | 公式跳跃从 `offset+2` 起步 | 有差异 | ✓ |
| B | 形状回退 `p-2` 而不是 `p-3` | 有差异 | ✓ |
| C | 公式魔数少查最后一个字节 | 有差异 | ✓ |
| F | 形状守卫分支步长写成 `+2` | 有差异 | ✓ |
| D | 形状锚点改用 `0x00`（超集枚举） | 无差异 | ✓ |
| E | 公式去掉内层 `offset >= limit` 守卫 | 无差异 | ✓ |

**对照 E 是我最初判断错误、被实测纠正的一条。** 我原以为去掉内层守卫会让扫描
越过 `limit`，实测零差异——因为 `while (offset < limit)` 的条件判断立刻会兜住。
把它从「改错」改标为「等价变体」，正是阴性对照该起的作用。

### 差分测试的两个陷阱（都踩过）

* **合成语料必须真的产出。** 公式的第一版合成块把 UTF-16LE 写成了
  `[0x00, charCode]`（解码是 `(data[i+1] << 8) | data[i]`，低字节在前），
  于是每个字符都被 `[^\x20-\x7E\\]` 过滤干净；而且所有合成缓冲区都不到 100 字节，
  扫描上限 `data.length - 100` 直接让循环一次都不进。**两个 bug 叠加的结果是
  差分测试完全空转**（两版都返回 `[]`，永远「一致」）。修法是写对字节序、
  把缓冲区垫到 320 字节，并把「必须有产出」写成断言。
* **对照 C 需要对齐的夹具。** 「少查一个字节」只有在错位后仍能解出可读文本时
  才会暴露；第一版夹具错位一字节，字符全被过滤掉，对照与正版都产出 0，
  又是空转。改成把文本对与 `offset` 对齐后才抓到。
* **对照 F 需要能进入守卫分支的形态。** 守卫分支只在扫描**恰好走到**某个偏移时
  才触发，而跳跃通常直接落到锚点上、跳过它。造出 `00 F0 00 F0` 重叠形态
  （链头用 `recVer=0` / `recInstance=0x00F0`）才能进入：偏移 `c-2` 前置筛通过但
  掩码拒绝、偏移 `c-1` 守卫触发、偏移 `c` 才是真链。
