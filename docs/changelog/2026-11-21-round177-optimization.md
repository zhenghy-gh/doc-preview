# Round 177 — 整轮否决（发布暂停模式）

**日期**：2026-11-21　**结论**：否决候选，未落地任何生产代码，版本保持 0.7.88。

## 候选

`decodeRangeWithoutGuard`（`src/utils/docparser/clxReader.ts`）复用模块级 `Uint16Array` / `Uint8Array` scratch 缓冲区，避免每次调用新建 typed-array 与末尾视图对象。

## 证据

- **剖析**（40 轮 × 27 份真实语料，`--cpu-prof`）：`decodeRangeWithoutGuard` 自耗 4.34%，GC 12.46%。
- **逐字节等价**：27 份 `parseWithFormat` 全量 JSON dump，`cmp` 完全一致，SHA-1 `6153f5bdfc8de0f849b6f8d1805991e8221f8009`，16,247,724 字节。
- **配对端到端**（同进程、base/cand 交错、4 组独立样本）：
  - 160 对：medianRatio 0.984441、胜 99/160 = 61.88%
  - 200 对：medianRatio 1.004734、胜 91/200 = 45.50%
  - 200 对：medianRatio 1.002894、胜 96/200 = 48.00%
  - 200 对：medianRatio 0.998324、胜 109/200 = 54.50%
  - **符号翻转**，胜率在 45%–62% 间漂移，3/4 组低于噪声地板（~54%）。

## 裁决

收益不可复现：首组的 1.6% 优势在后续干净样本中消失甚至反号。按 `optimization-loop.md` 硬纪律「实测退化/符号翻转即否决」，**撤回全部生产代码**（`git checkout -- src/utils/docparser/clxReader.ts`，已核对工作区干净）。

## 教训（通用教训 15）

剖析中「分配 + GC」占比高不等于「复用缓冲区就能赢」：当被复用的对象只是**短命小视图**（`subarray` 本身仍分配视图对象），省下的分配可能小于缓存/复用带来的额外簿记。必须先做调用计数与隔离基准，再决定是否值得进端到端。
