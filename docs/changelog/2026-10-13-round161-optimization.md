## 先量后改

### 1) 真实调用尺寸分布（插桩）

在 bundle 的 `bytesToBase64` 入口插一条 `(globalThis.__B64 ||= []).push(bytes.length)`，跑 27 份样本 × 20 轮：

| 分档 | 调用数（20 轮） | 字节数 | 字节占比 |
|---|---|---|---|
| ≤ 1 KB | 820 | 289,440 | **0.92%** |
| 1 KB – 8 KB | 440 | 963,600 | **3.08%** |
| > 8 KB | **60** | 30,057,620 | **96.00%** |
| 合计 | 1320（**66 次/轮**） | 31,310,660（**1.493 MB/轮**） | 100% |

最大单次 **979,410 字节**。⇒ 96% 的字节量集中在 60 次大调用上，**分块大小只对这批大调用有意义**；同时它也是 `bytesToBase64` 成为 GC 大户（整轮 GC 10.79%）的主要来源之一（每轮要产出约 1.49 MB 中间串 + 1.99 MB base64 串）。

### 2) 真实分布回放（本轮的关键测量口径）

先前的微基准都用**合成**尺寸（且 `0x800`/`0x400` 从未被测过）。本轮改为**逐条回放真实尺寸**：把插桩得到的 1320 个尺寸存成 JSON，每个变体按同一序列重跑全部 20 轮，7 个变体在同一进程内交错 12 次取中位。

| 变体 | 中位（ms，= 全部 20 轮） | 比值 | 折算每轮 |
|---|---|---|---|
| `0x2000`（现状） | 79.183 | 1.0000 | 3.959 ms |
| `0x1000` | 71.654 | 0.9049 | 3.583 ms |
| `0x400` | 69.652 | 0.8796 | 3.483 ms |
| **`0x800`（采纳）** | **68.805** | **0.8689** | **3.440 ms** |
| `0x200` | 72.304 | 0.9131 | 3.615 ms |
| `0x400` + `≤100k` 单次 apply | 70.877 | 0.8951 | 3.544 ms |
| `0x2000` + `≤100k` 单次 apply | 82.079 | 1.0366 | 4.104 ms |

隔离收益 **−0.519 ms/轮**。所有变体在 57 个不同尺寸上输出逐字符相同（回放脚本内断言）。

### 3) 与 Round 103 历史注释的调和（重要）

`binaryReader.ts` 原注释写「`0x1000` 5.97 ms、`0x2000` 6.02 ms、`0x4000` 8.17 ms、`0x8000` 7.71 ms ⇒ 取 0x2000」。核对后**不矛盾**：那次只测了 `0x1000` 及以上，**从未测过更小的块**，`0x1000` 与 `0x2000` 在噪声内遂取大者。本轮补上 `0x800`/`0x400`/`0x200` 三点后才看出拐点在 2 KB 附近。注释已按本轮实测重写（保留历史数据并注明其覆盖边界）。

## 候选实现（`src/utils/binaryReader.ts`）

只改一行常量 + 重写说明注释：

```diff
-  const CHUNK = 0x2000
+  const CHUNK = 0x800
```

函数结构与分支完全不动（`bytes.length <= CHUNK` 走单次 `apply`；否则攒块 → 一次 `join` → 一次 `btoa`）。

**为什么这是「减少真实工作」而非「减少分配」**：块数从 ⌈n/8192⌉ 降到 ⌈n/2048⌉ 会**增加** `subarray` 视图与 `apply` 调用次数，却仍然更快——省下的是 `String.fromCharCode.apply` 在单块内**逐字符走慢路径**的成本（`apply` 实参越多越接近 V8 的慢路径拐点；实测 100 000 个实参可用、125 000 抛 `RangeError`）。这与 R149/150/153/154「只减分配 ⇒ 中性」的分野一致，与 R156/157/158/160「砍掉真实加载/调用/扫描 ⇒ 正收益」同侧。

## 被否决 / 未采用的候选（备记）

### A. OLE 循环检测 `Set` → `Uint8Array` 位图（4 处）+ `resolveStyleFormat` `Set` → `chain.some`（**否决**）

- 插桩实测 `visited` 操作 **48,652 次/轮**（24,326 `has` + 24,326 `add`）：`readRegularStream` 19,169（78.8%）、`resolveStyleFormat` 4,963（20.4%）、`readMiniStream` 99、`getDirectorySectors` 86、`getMiniFatSectors` 10。
- 候选 bundle 与基线**逐字节等价**（27 份 SHA-1 同 `8f127d0b…`）。
- 性能：300 对 中位 0.99275 / 均值 0.9999 / 胜 55.67%（看着像小赢）→ **800 对 0.99849 / 均值 0.99948 / 胜 413 = 51.6%**。均值中性、胜率**低于 ~54% 噪声地板**，是典型的「小样本 +0.7% ⇒ 放大后归零」噪声特征（同 R149/150/154）。
- 按协议撤回（`git checkout` 还原），不升号。**注：本轮负控脚本第一次还原时误用 `git checkout` 把未提交的 base64 改动一并还原**，随后按 sha256 比对重新应用（`80030adc…`）并复跑护栏与 bundle 重建校验（见「等价性」）。

### B. OLE 天花板探针（诊断用，行为改变、不可采纳）

把 6 处循环检测**整体删除**（含 `logger.warn` 与 `break`，仅保留循环）后 400 对：**0.9883 / 均值 0.99453 / 胜 61.0%**。

⇒ 该空间确有约 **0.5–1.2%** 的上限，但 **A 方案拿不到**，因为它只是把「`Set` 分配 + 哈希」换成「`Uint8Array` 分配 + 下标读写」——**分配成本抵消了哈希节省**。真正能吃下上限的实现必须**同时消掉分配**（例如世代戳共享位图：模块级 `Uint32Array` + 每调用自增 epoch，`visited[i] === epoch` 判环，无需清零、无需分配）。留作 **Round 162 候选**。

### C. 其他

- `≤100 000` 字节一律单次 `apply`（省掉 `join`）：**1.0366× 更慢** ⇒ 否。块越大越接近慢路径拐点，这与「`0x4000` 以上反而变慢」同因。
- 逐步 `binary +=` 替代 `parts.join('')`：无差异（历史实测 6.02 vs 5.98 ms）⇒ 保留更简单的 `join`。
- 分块 `btoa` 后拼接 base64（R148 已否决，0.968×）⇒ 未再试。

## 护栏（`tests/binaryReader.round161.test.ts`，14 项）

**核心难点**：该函数对**任意**块大小都输出同一字符串（分块只影响怎么攒中间串）。因此任何「比输出」的测试都无法发现块大小被改回去 —— 唯一能钉死本轮生效的是**源码文本断言**。

- **A 组（等价性，oracle 用与分块无关的逐字节拼接 `naive()`）**：A1 全部 256 个单字节 + 全部 65536 个双字节组合；A2 新边界 `0x800` 前后 27 个尺寸逐点扫（含 `0x7fe/0x7ff/0x800/0x801/0x802`、`0x1800` 系列、旧边界 `0x1ffe…0x2001`）；A3 长度 mod 3 的三种余数 × 6 个块交界；A4 每个字节值跨过 `0x800` 边界（块尾与下一块首字节的 256 种组合）；A5 真实语料 6 段切片（>5 MB）与 `naive()` 一致**且断言确有切片长于 `CHUNK`**（非空转）；A6 1 MB 输入（跨 512 块）。
- **E 组（骨架负控，证明 A 组判据非空转）**：与生产同构的 `skeleton()` 注入三种破坏 —— E2 丢最后一块、E3 块顺序颠倒、E4 隔块丢弃，均须与 `naive()` 不同；E5 三种破坏在 A2 的边界集合上全部可辨（并特意保留 `0x800` 这一「单块、三种破坏都无影响」的尺寸，使断言 `>0` 有意义）。
- **D 组（接线元断言）**：D1 **源码中 `const CHUNK = 0x800` 存在且 `const CHUNK = 0x2000` 不存在**；D2 长输入仍走「攒块 + 一次 `join` + 一次 `btoa`」、短输入走单次转换；D3 显式证明「三种块大小输出逐字符相同」，作为 D1 为何必须查源码而非比输出的元论证。

**离树负控**（注入生产源码 `src/utils/binaryReader.ts`，跑完即还原）：

| 注入 | 失败项数 |
|---|---|
| N1 `0x800 → 0x1000`（**输出不变**，只有 D1 能抓） | **1 failed** / 13 passed |
| N2 块步长 `CHUNK → CHUNK + 1`（块间漏 1 字节） | **7 failed** / 7 passed |
| N3 `parts.push → parts.unshift`（块序颠倒） | **6 failed** / 8 passed |
| N4 `end = Math.min(i + CHUNK, bytes.length - 1)`（末块截断 1 字节） | **7 failed** / 7 passed |

N1 只被 D1 一项抓住，直接验证了「源码断言不可省」。四组注入后源码 sha256 恢复为 `80030adc6827241f8bdb4fe28941b488e1d336935c932f15b7ae9e1e0c5c241e`（与注入前一致），护栏复跑 14/14。
