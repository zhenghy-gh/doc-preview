# 续篇：上篇说"放弃读 CHP/PAP"，我花半年把它读完了

先给没看过上篇的朋友三句话回顾：我用 AI 写了个纯前端的 .doc 解析器（标题就叫《我用 AI 写了一个 .doc 解析器，0 依赖 11KB 跑在 Vue 3 上》，链接：https://blog.csdn.net/weixin_44397261/article/details/162105614），OLE2 容器解析 + 5 阶段管线，为了控制体积放弃了读 CHP/PAP 二进制格式表，用启发式规则"猜"格式，号称 80% 准确度，11KB gzipped，发到了 npm 0.3.3。

当时评论区有人问：你说的 80% 准确度，到底是哪些格式会丢？

我回了一句"基本盘都没问题"。然后被一份红头文件教做人了。

## 一份红头文件，把我问住了

有个做档案系统的哥们儿，直接把单位的一份红头文件甩到我仓库 issue 里。我打开自己项目的 demo 一看，标题字号是对的，但正文的仿宋全变成了默认字体，落款日期跑到左边去了，段首缩进没了。

那晚我对着 hex dump 看了很久，想明白一件事：**启发式规则在 demo 文件上永远够用，在真实文件上永远不够用**。80% 准确度，说白了就是"最常见的 20% 场景我不敢保证"。

于是我把上次省下的活，又老老实实补了回来。仓库从 0.3.3 走到 0.7.3，功能清单从一页纸变成一整页（[FEATURES.md](https://github.com/zhenghy-gh/doc-preview/blob/main/FEATURES.md)，118 项已实现）。这篇是补课复盘，也是给上篇的正式勘误。

## 为什么反悔：三个原因

**真实用户反馈。** 红头文件只是第一个，后面还有合同（条款编号乱）、论文（脚注错位）、规章制度（修订痕迹全丢）。内网文档千篇一律？真不是，每个品类都有自己的坑。

**需求升级了。** 最初只要求"能看"。后来用户要导出、要打印对比、要显示修订痕迹——这些功能没有真实的格式信息根本做不出来，靠猜的格式导出出去就是一堆错。

**AI 读规范比我预想得快。** 之前那篇说"完整读 CHP/PAP 要再写 2000 行"，实际动手发现，让 AI 照着 MS-DOC 规范一章一章翻译成代码，几乎一遍过。这个观察放到最后细说。

## 补课第一站：SPRM 自造码换成规范码

.doc 里字符和段落格式全是 SPRM（Single Property Modifier）编码的，每个 SPRM 有规范编号：加粗是 0x0835，字号是 0x0A35。早期版本我图省事用了一套自造码，后果就是自己造的文件测着没问题，换真实文件就丢格式。

迁到规范码之后长这样：

```ts
case 0x0835: // sprmCFBold
  format.bold = operand !== 0
  break
case 0x0A35: // sprmHps，字号，单位是半磅
  format.fontSize = Math.round(readUInt16(operand) / 2)
  break
```

这次迁移的提交信息我留到现在，原话是"修复真实文件字符格式全部丢失"。现在说起来轻巧，当时满屏乱格式的截图我存了一文件夹。

## 补课第二站：FKP 和样式表

Word 97+ 的格式不在正文里，存在独立的 FKP 页（bin 表）中，用 PlcfBteChpx、PlcfBtePapx 两个索引表定位。这一段是纯体力活：读规范、对着偏移数格子、写解析函数。做完之后，真实文件的 CHPX/PAPX 才算真正恢复——字体字号、加粗斜体下划线、上下标、颜色高亮、缩进行距、制表位，一个不落——这部分是最解气的。

样式表（STSH）是另一块硬骨头。它决定文档的"地基"：正文基于什么样式、标题继承谁、局部覆盖怎么合并。解析完 STSH，样式格式恢复从 0 跳到平均每文档 65 个，沿 istdBase 链合并继承，还得防循环引用把自己绕进去。

v0.4.0 之后，字符和段落格式不再靠猜，直接读。启发式规则彻底降级成兜底。

## 上一篇 FAQ 里说"暂时没解析"的，逐条还债

上篇结尾挂了个问答清单，现在挨个对照：

**Q：支持图片吗？** 上篇：不支持。现在：PICF/FCPic 结构解析 + Data 流魔数扫描双保险，图片能内联渲染到对应段落，还能标出格式和尺寸。

**Q：支持表格吗？** 上篇：不支持。现在：TAP SPRM 解析，单元格边框、水平垂直合并（colspan/rowspan）、嵌套表格递归渲染、对齐缩进都有。有个细节——表格渲染专门对照 WPS 的输出调过，国内用户手里 WPS 生成的表格占比真不小。

**Q：图表、公式呢？** 上篇：没解析。现在：都是 OLE 对象，从目录表认出来再解析。公式能从 eqn 格式转成 LaTeX，图表能识别柱状图折线图饼图，艺术字能提取文本和效果。

**Q：修订模式呢？** 上篇：不支持。现在：作者表 + RMRK 结构 + DTTM 时间戳，渲染支持"标记/接受/拒绝"三模式一键切换。这个功能后来被好几个做审稿系统的同学问过。

**Q：能解析 macOS Pages / WPS 写的 .doc 吗？** 上篇：能解析但有坑。现在：textutil 的 0xBF 编码坑专门做了兼容（之前第六节那个），WPS 的表格输出也专门调过。

除此之外还补了：页眉页脚（PlcfHdd 按文档标志拆首页/奇偶页）、分节分栏（SEPX + CSS 真实分栏）、TOC 域（\o \h \n \z 各种开关）、索引域、交叉引用、书签跳转、Word 版本检测（nFib 识别 6.0 到 2007+）、样式集检测。不一一列了，想看全的翻 FEATURES.md。

## 渲染层也重写了

DocPreview.vue 从一千多行长到六千多行，能干的事也多了一截：分页渲染、虚拟滚动、真实分栏、修订三模式切换、导出 Markdown；搜索做了高亮，还能选大小写和全词匹配；制表位是先用 Canvas 量好宽度再渲染的，对齐效果跟 Word 里一致；中英双语、暗黑模式、移动端适配这些属于标配，加载进度条和错误分类重试也安排上了。

最花时间的是虚拟滚动。最初做完分页渲染，发现 10MB 的文档滚动起来白屏几秒——不是解析慢，是 DOM 太多。改成只渲染可视页 ±1 缓冲 + 高度缓存，才把帧率救回来。搜索的时候还得临时禁用虚拟滚动，不然高亮跳转找不到目标页。这类性能细节，之前那篇说"AI 不会主动给你跑 A/B 实验"，这次依然成立，全是我自己一遍遍滚出来的。

## 73 个提交，一半在修边角

仓库 73 个提交，v0.7.3 之后那二十多个几乎全是鲁棒性修复。挑几个印象深的：

- 排除 FAT 里的文件头幽灵扇区（文件系统把 header 扇区串进链里）
- 正确解码 OLE 目录名称的终止符（差一个字节，文件名全乱）
- 支持超过千段的合法 CLX Piece Table（超长文档之前直接报错）
- 拒绝未对齐的压缩 Piece FC（8-bit 压缩的 FC 必须 2 字节对齐）
- 限制 MiniFAT 声明容量、归一化不安全的 CFB 扇区参数（恶意文件不再让解析器崩）

这类 bug 的共同点：测试用例里根本造不出来，全是真实文件喂出来的。所以 docs/ 里现在躺了 27 个真实 .doc 样本，从 32KB 到 1.5MB，还有专门的 textutil、WPS 产物。每次改解析器，先跑一遍"27 个样本全部正常提取"再说。测试也堆到 29 个文件 570+ 用例，光 oleParser 就 68 个。上篇说"覆盖率 91% 才算够"，这次不仅没降，还加了性能回归测试。

## 上篇没展开的：AI 协作的新观察

上篇说 AI 在性能微调和边界 case 上会卡住，这个结论现在依然成立。但这半年我发现它有个反直觉的强项：

**规范解析是 AI 的舒适区，比写启发式规则顺手得多。** SPRM 解码、FKP 遍历、STSH 偏移计算，这种"照着规范翻译成代码"的活，AI 几乎一次写对。反倒是启发式规则那种需要业务直觉的，AI 给的全是套路。领域越封闭、规范越明确，AI 完成度越高——这个结论我是在连续让 AI 啃了三个 MS-DOC 章节之后才敢说的。

**迁移类重构，AI 是主力。** 自造码迁规范码、大文件拆 28 个模块，机械但量大，人定目标和验收标准，AI 批量执行，效率是手写的三五倍。

**边界 case 依然得靠人。** 幽灵扇区、终止符、未对齐 FC，靠的是对真实文件的 hex dump 观察，AI 不会主动发现。我的体感是：样本库比测试用例更重要。测试证明逻辑对，样本证明真实文件对，两个都得有，缺一个就会在某个犄角旮旯翻车。

## 得说清楚的代价

上一版标题里有"11KB"，现在这个数字没了，先跟冲着极简来的朋友道个歉。解析器从 1900 行长到两万多行（含 UI），包确实大了。但换来的是字符级样式段、样式继承、分节分栏、修订痕迹、结构化图片公式图表数据——而且依然零运行时依赖，Vue 只是 peer。

两万多行里大部分是规范结构解析，不是业务逻辑。哪天有人想做 .doc 转 PDF 或转纯文本，这层可以直接搬走。这大概就是写解析器最爽的地方。

## 最后，回应上篇

当时那篇结尾我写："如果你正好也卡在这，欢迎把场景发到评论区，我看看能不能给你 demo 测一下。"（原篇在这：https://blog.csdn.net/weixin_44397261/article/details/162105614）评论区确实来了不少场景，这份红头文件就是其中之一。这篇算是把上篇欠的账还了一部分：格式从猜变成读，"不支持"清单基本清空。

回头想想，当时那个"80% 够用"的决定，本质上是在偷懒。真把补课做完，发现代价没有想象中大——因为 AI 把"读规范"的成本打下来了。所以这篇的结论就一句：**别让"够用"变成天花板，尤其是补课的成本已经被工具砍到很低的时候。**

手里还有解析不了的 .doc 的，欢迎继续丢 issue。那种带真实文件的报错，修复优先级最高。
